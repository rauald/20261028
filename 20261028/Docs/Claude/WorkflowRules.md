# Workflow 규칙

> Claude가 업무 수행 시 지켜야 하는 업무 프로세스
>
> 해당 문서에 기재되지 않은 업무가 발생할 경우, 이 지침에 대한 개선을 사용자에게 권유한다.

---

## 0. 전체 흐름

```
[개발] / [버그 수정]
   └─(명령)─> Github Issues ─> 브랜치 생성 ─(착수명령)─> 브리핑 ─> 작업 ─> 확인 ─(승인)─> Commit / Push ─> PR ─> 병합 ─> 현재 브랜치 삭제 ─> Issue Close
                                                                    ↑          │
                                                                    └─(반려)───┘
[문서 작업]
   └─(착수명령)─> 작업 ─> 확인 ─(승인)─> Commit / Push ─> PR ─> 병합
                   ↑          │
                   └─(반려)───┘
```

- 각 단계는 앞 단계가 끝나야 진행한다. 단계를 건너뛰지 않는다.
- 각 단계의 수행 주체는 아래 표를 따른다.

| 단계 | 수행 주체 |
| --- | --- |
| Github Issues | Claude (사용자 승인 후) |
| 브랜치 생성 | 사용자 |
| 브리핑 | Claude |
| 작업 | Claude |
| 확인 | 사용자 |
| Commit / Push | 사용자 |
| PR | Claude (사용자 요청 시) |
| 병합 | 사용자 |
| 현재 브랜치 삭제 | 사용자 |
| Issue Close | Claude (사용자 요청 시) |

## 1. 업무 유형

> 명령을 받으면 먼저 업무 유형을 구분한다. 유형에 따라 진입 경로가 다르다.

- 개발 : 새로운 기능을 추가하거나 기존 기능을 개선한다.
- 버그 수정 : 오류 또는 예상과 다른 동작을 수정한다.
- 문서 작업 : `Docs/` 하위 문서를 작성하거나 수정한다.
- 유형이 불분명하면 임의로 정하지 않고 사용자에게 질문한다.
- 문서 작업 중 소스코드 변경이 필요해지면 작업을 멈추고, 개발 경로로 전환할지 사용자에게 질문한다.

## 2. Github Issues

> 개발, 버그 수정 업무에 적용한다. 문서 작업은 이슈를 등록하지 않는다.

- 명령을 받으면 이슈로 등록할 필요가 있는지 판단한다.
- 필요하다고 판단하면 판단 근거와 함께 사용자에게 이슈 작성을 권유한다.
- 이슈 권유부터 등록까지는 `github-issue` 스킬로 수행한다. 작성 규칙은 `Docs\Documentation\Github Issue Rule.md`를 따른다.
- 이슈 없이 진행할지 여부는 사용자에게 확인한다.

## 3. 브랜치 생성

> 개발, 버그 수정 업무에 적용한다. 브랜치는 사용자가 직접 생성한다.

- Claude는 브랜치를 생성하거나 전환하지 않는다.
- 이슈 작성 후, 사용자가 브랜치를 생성하고 착수명령을 내릴 때까지 대기한다.
- 착수명령을 받으면 현재 브랜치를 확인한다.
  - `main`, `Develop` 브랜치인 경우 `CLAUDE.md`의 절대 원칙에 따라 작업을 거부한다.
  - 브랜치 이름이 해당 이슈와 대응하지 않는 경우 사용자에게 알린다.
- 문서 작업은 별도의 브랜치 생성 단계를 거치지 않는다. 단, 현재 브랜치가 `main`, `Develop`인 경우 위 절대 원칙이 동일하게 적용된다.

## 4. 브리핑

> 개발, 버그 수정 업무의 착수 전 작업 계획을 보고한다. 문서 작업은 브리핑하지 않는다.

- 브리핑 양식은 `Docs\Claude\ClaudeCodeRules.md`의 `기능 구현 착수 규칙`을 따른다.
- 기존 기능을 수정하거나 연관된 기능을 개발하는 경우, 기존에 작성된 기술문서와 다이어그램을 검토한 후 작업 계획을 수립한다.
- 검토한 문서는 브리핑에 함께 기재한다. 검토할 문서가 없으면 그 사실을 기재한다.
- 사용자의 승인을 받기 전에는 작업에 착수하지 않는다.
- 예시
    ```markdown
    **검토 문서**
    - `Docs/TechSpec.md` : 유저 입력 시스템 규칙 확인
    - 다이어그램 : 관련 다이어그램 없음
    ```

## 5. 작업

> 승인된 범위 안에서만 작업한다.

- 개발, 버그 수정 : 브리핑에서 승인받은 파일과 기능만 작업한다. 작업 범위는 `Docs\Claude\ClaudeCodeRules.md`의 `작업 범위 규칙`을 따른다.
- 문서 작업 : 착수명령을 받은 문서만 작업한다.
- 작업 중 범위 변경이 필요하면 작업을 멈추고 사용자에게 보고한다. 개발, 버그 수정은 브리핑을 다시 수행한다.
- 작업이 끝나면 `Docs\AI-Standards\GeneralRules.md`의 `완료 보고`에 따라 보고하고 확인 단계로 넘어간다.

## 6. 확인 (사용자 검수)

> 작업 결과는 사용자의 승인을 받아야 완료된다.

- 완료 보고 후 사용자의 검수 결과를 기다린다. Claude가 스스로 승인된 것으로 간주하지 않는다.
- 승인 : Commit / Push 단계로 넘어간다.
- 반려 : 반려 사유를 정리하고 작업 단계로 돌아간다.
  - 반려 사유가 불명확하면 사용자에게 질문한다.
  - 반려 사유가 브리핑 범위를 벗어나면 브리핑을 다시 수행한다.
- 예시
    ```markdown
    ## 반려 반영 : [n차]

    **반려 사유**
    - 

    **수정 계획**
    - 
    ```

## 7. Commit / Push

> Commit / Push는 사용자가 직접 수행한다.

- Claude는 Commit, Push를 수행하지 않는다.
- 사용자 검수에서 승인된 이후에 진행한다.

## 8. PR

> PR은 사용자의 요청이 있을 때 Claude가 생성한다.

- 사용자의 Push가 완료된 것을 확인한 후 생성한다.
- 작성 양식은 `Docs\Template\PRTemplate.md`를 따른다.
- 연관된 Github Issue가 있으면 PR 본문에 언급한다.
- PR의 대상 브랜치는 사용자에게 확인한다.

## 9. 병합

> 병합은 사용자가 직접 수행한다.

- Claude는 병합을 수행하지 않는다.
- 문서 작업은 이 단계에서 업무가 종료된다.

## 10. 현재 브랜치 삭제

> 개발, 버그 수정 업무에 적용한다. 브랜치는 사용자가 직접 삭제한다.

- Claude는 브랜치를 삭제하지 않는다.
- 병합이 완료된 이후에 진행한다.
- 문서 작업은 별도의 브랜치를 생성하지 않으므로 이 단계를 거치지 않는다.

## 11. Issue Close

> 개발, 버그 수정 업무에 적용한다. 사용자의 요청이 있을 때 Claude가 Issue를 닫는다.

- 병합과 브랜치 삭제가 완료된 것을 확인한 후 진행한다.
- Issue를 닫기 전, 해당 Issue의 `완료조건 (DoD)` 체크리스트가 모두 충족되었는지 확인한다.
  - 충족되지 않은 항목이 있으면 Issue를 닫지 않고 사용자에게 보고한다.
- 이 단계가 끝나면 업무가 종료된다.
- Issue가 없는 단계는 이 업무를 넘어간다.
